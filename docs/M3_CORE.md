# M3 core runbook

This runbook describes the reconstructed M3 backend currently in the tree. M3 establishes public-data contracts, a strict DAG verifier, deterministic serial execution, backend analysis operators, an isolated generated-operator worker, and the model comparison/development integration. The original E4 operator implementation and its eleven seed playbooks were not located; these operators and six seed playbooks are explicit reconstructions. The fixed ten scored cases and two development cases remain frozen. Scored labels must not be read or used to choose operators, thresholds, seeds, model settings, or repairs. The ten scored predictions, M4's three-attempt controller/bootstrap/admission, and the later baseline comparison are outside this milestone.

## Inputs and identity

`e4core.adapter.load_case(case_id, split)` accepts only `split="dev"` or `"scored"` and loads one `public/cases/<incident_id>/` directory plus `public/deployment_catalog.json`. It verifies the frozen sample, public manifest, clip manifest, catalog, case file hashes, and row counts. It does not read raw full-day files, other cases, gold labels, or audit reports. The mount supplied to model-generated operators must preserve that boundary. The case's preceding reference and alert intervals are half-open UTC epoch-millisecond windows; local UTC+8 metadata is checked against those boundaries. The reference interval has coverage, not a guarantee of healthy behavior.

`EntityRef` retains the entity's role and original identifier. Executing container/component (`cmdb_id`), logical service (`serviceName`), database target (`dsName`), deployment group, and host relationships remain distinct. A merged container group is not an alias for an individual Docker component. Acceptance and final duplicate handling use stripped, case-folded component identifiers only; there are no inferred aliases. The answer retains five distinct component leads, while eventual primary acceptance is component identity in positions 1–3. Component-plus-category is secondary. Leave category `null` unless an evidence-backed category classifier exists; analysis-family names are not fault categories.

The adapter preserves repeated metric rows and reports their counts. `metric_app` series use service/field identity; duplicates at a timestamp are median-collapsed, then window summaries use the median across timestamps. Other metric identity includes source table, component, metric name, BOMC ID, and item ID. Invalid/nonfinite numeric values remain quality/missingness evidence. Trace spans are identified by `(traceId,id)` and parent IDs resolve only inside their trace. `success` accepts case-insensitive true/false; missing or unknown tokens stay invalid. A span's executing component, logical service, and database target stay separate. Unresolved parent links are marked as possibly clipped and are never repaired by reading outside the case. Source `elapsedTime` and `avg_time` units are unresolved; only within-field elapsed-time comparisons are supported, and no conversion to timestamps or app averages is made.

## Runtime, DAG, and execution

The schema is `config/runtime_schema.json`; defaults are in `config/core_runtime.json`, and the contract/resolution decisions are in `config/core_contracts.json`. `runtime.dag_depth` is the configured maximum operator-node path depth, not measured depth. Runtime also declares the 40-node cap, five internal leads/top-three cutoff, seed 42, support and resampling settings, block/tail settings, numeric floors and eligibility thresholds, flow fit gates, and family weights. Case windows come from the verified public case manifest. Measured node count and graph depth are outputs, not writable limits. The resolver applies explicit parameter, explicit `runtime.<field>` binding, operator runtime field, then static default; unresolved required values and non-nullable explicit nulls fail. `auto` is accepted only for a declared estimator, which receives reference-window data only. Resolved values and provenance are recorded.

An `e4-dag/1` document has ordered `nodes` and exactly one `{"node": id}` return. Each node has a unique ID, registered operator and exact version, named input references to earlier nodes, `params`, and optional `bindings`. The verifier checks types/arity, references, cycles/forward refs, unused bindings, candidate-to-scorer flow, parameters/runtime paths, graph limits, and a scored sink for each candidate branch. The final return combines the remaining scored sinks. Aggregates are created for one named window (`reference` or `alert`); downstream scorers compare them. See `examples/synthetic_shared_dag.json` for a branching/shared-intermediate example and `examples/runtime_binding_examples.json` for binding cases.

`SerialExecutor` evaluates verified nodes in dependency order and computes shared nodes once. Its inspectable records include resolved parameters and provenance, inputs, timing, rows/bytes, errors, and cache decisions. Cache identity includes case/data and window digests, dependencies, schema/adapter/runtime and operator versions, resolved context, and seed; failed/partial outputs cannot be reused as valid nodes. The conservative runtime snapshot makes a used context change such as `runtime.dag_depth` invalidate dependent entries. The first actual development run produced equal cache-cold/warm/cache-disabled answers in one process, but later review found dependency permutation observations came from an unordered trace-ID set. Luna added canonical trace-ID ordering. The synthetic regression now returns `323957751.6576788` identically under ten `PYTHONHASHSEED` values; the prior scores ranged from `288739499.8465` to `370774392.8644`. The post-fix release suite passed 104/104 tests. A fresh-process cache-cold/warm/disabled replay of the saved development DAG then passed under `PYTHONHASHSEED=1` and fixed numerical-library thread counts. See [M3_RESULTS.md](M3_RESULTS.md) for its artifact and remaining evaluation boundary.

## Reconstructed backend operators

`e4core.telecom_ops.telecom_registry()` registers data injection, per-window metric and trace aggregation, label-free candidate generation, metric/error/latency contrasts, conditional flow contribution, dependency propagation, and answer combination. These are the six intended analysis families: metric contrast, trace error contrast, trace latency contrast, KPI/flow attribution, dependency adjustment, and combined evidence. Candidate generation uses the public catalog and observed backend roles, not evaluator fields.

Metric series collapse duplicate timestamps before inference. Declared cumulative counters become reset-aware first-difference rates (current value/elapsed minutes after a negative reset; no first rate without an in-view predecessor). Unknown metric semantics remain descriptive and cannot rank. Metric changes use median and configured tail contrasts on nonoverlapping five-minute block summaries; the runtime default is 499 deterministic permutation resamples. Evidence needs 12 distinct timestamps per window and at least four independent blocks per window. Scale is `max(1.4826 × reference MAD, |reference median| × relative_scale_floor, absolute_scale_floor)`. The normalized effect is alert-minus-reference divided by that scale; ranking strength is `|effect| × -log10(max(p, p_score_floor))`. Eligibility also requires the configured 0.5 absolute normalized-effect minimum and p ≤ 0.1, plus any declared metric direction. App average latency abstains when per-minute request support is below five; request counts are context/support, not independent causes.

Trace error and latency observations use one per-trace/entity/call-type summary to avoid counting spans as independent requests. Error evidence compares per-trace failure fractions; latency evidence compares within-field `elapsedTime` median/tail distributions. They require 12 independent trace IDs per window, positive degradation, normalized effect at least 0.5, and permutation p ≤ 0.1. Missing/invalid success or duration values do not become successes or numeric values.

Dependency evidence resolves only same-trace, same-window parent links. A direct failed span has weight 1; a failed span marked as propagated to an ancestor contributes 0.25 to that entity; the deployment host receives 0.2 of the span weight. Per-trace weights are capped at their maximum observed contribution, then reference/alert weighted failure means are contrasted. Missing edges remain missing. The same support/effect/p thresholds gate ranking. This is a backend reconstruction, not MoCE's client-flow method.

Conditional flow fits L1 regression of root OSB `elapsedTime` on same-trace non-root backend span elapsed times, with one feature per role/entity and per-trace median values. It excludes the root target from predictors, uses reference plus alert traces for fitting and median imputation, and abstains if fewer than 30 matched traces or eligible feature observations per window, if inputs are nonvariable, if absolute feature correlation is ≥ 0.98, if outcomes are nonfinite/constant, if R² < 0.5, or if root mean latency does not degrade. It also requires exactly one logical root OSB service across eligible matched traces and no eligible trace with multiple root OSB services; otherwise it abstains as `ambiguous_root_kpi_service` and reports service IDs and counts. For feature j, contribution is `beta_j × (mean_alert(x_j) − mean_reference(x_j))`; eligibility also requires a positive contribution, normalized effect ≥ 0.5 and at least 0.2 of the root mean change. Fit scope and limitations appear in evidence. This is explicitly a backend adaptation inspired by MoCE, not a client expert reproduction; client/session/cohort features are unavailable. A development case with mixed or ambiguous root services can therefore leave flow unsupported while other branches still run.

The combiner first merges role variants with the same canonical component ID within each family, keeping the strongest score and distinct evidence. Each eligible family's positive scores are divided by that family's maximum positive score. The weighted contributions are summed and divided by the common total weight of eligible families; an absent family contributes zero. Thus scorer variants do not multiply a family's vote, and zero/no-evidence candidates cannot fill ranks. Ties sort by canonical ID then role. Category remains unknown unless a separate classifier supplies it.

Statistical results are exploratory change evidence. Per-series permutation p-values and choosing the maximum score across many series are not corrected causal probabilities; testing many correlated series can produce false leads. Five-minute blocks reduce serial dependence but only approximate independent observations. A p-value at or below 0.1 is an eligibility threshold for a diagnostic lead, not confidence that the entity caused the incident. Eventual evaluation, rather than these thresholds, measures component top-three accuracy.

The six generic seeds are the matching examples in `config/generic_seed_library.json` and builders in `e4core.telecom_ops`; each uses the public registry and verifier. Their per-seed prerequisites, abstention rules, and provenance are:

| Seed / purpose | Required tables, fields, and roles | Applicability and abstention | Origin |
| --- | --- | --- | --- |
| `metric` — rank component/service metric changes | `metric_app.csv`: `serviceName`, `startTime`, `avg_time`, `num`; other metric CSVs: `timestamp`, `cmdb_id`, `name`, `bomc_id`, `itemid`, `value`. Roles are service for app metrics and component for other metrics. | Needs paired reference/alert series and sufficient support (12 distinct timestamps; at least four five-minute blocks). Unknown metric kinds remain descriptive-only. `avg_time` also requires request support. | Reconstructed E4 metric-contrast family; robust mean/tail contrast is informed by MoCE methods, not a copied client expert. |
| `trace_error` — rank entities associated with rising request failures | `trace_span.csv`: `traceId`, `callType`, `success`, `cmdb_id`, `serviceName`, `dsName`. Independent unit is trace ID; roles are executing component, logical service, and database target. | Needs valid true/false statuses and at least 12 independent traces in each window per comparable entity/call type. Missing/invalid statuses do not enter the denominator; weak support abstains. | Reconstructed E4 trace-error family; no client-specific MoCE inputs are available. |
| `trace_latency` — rank entities with increased span latency | `trace_span.csv`: `traceId`, `callType`, `elapsedTime`, `cmdb_id`, `serviceName`, `dsName`. Roles are executing component, logical service, and database target. | Needs finite within-field `elapsedTime` and at least 12 trace IDs per window. Compares per-trace latency median/tail only; absolute units remain unresolved and cross-field conversion is unsupported. | Reconstructed E4 trace-latency family; tail-contrast design is MoCE-informed, not a client expert reproduction. |
| `conditional_flow` — attribute root OSB latency change to same-trace backend features | `trace_span.csv`: root OSB `callType`, empty `pid`, logical `serviceName`, `traceId`, `elapsedTime`; non-root same-trace `traceId`, `callType`, `elapsedTime`, and entity-role columns `cmdb_id`, `serviceName`, `dsName`. | Requires exactly one root OSB logical service among eligible matched traces and no multi-root-service trace; ambiguous/mixed service evidence returns `ambiguous_root_kpi_service`. Also requires at least 30 matched root traces overall and 30 observations for each eligible feature in each window, variable/non-collinear features, R² ≥ 0.5, and degrading root latency; otherwise abstains. | Reconstructed E4 KPI/flow family, adapted from MoCE conditional contribution to backend request traces. | `dependency` — reduce propagated-failure evidence and use deployment relationships | `trace_span.csv`: `traceId`, `id`, `pid`, `callType`, `success`, `cmdb_id`, `serviceName`, `dsName`; static deployment catalog for container/component-to-host and group relationships. Roles remain component, service, and database. | Uses only same-trace, same-window resolved parent edges. Needs valid failure evidence and 12 trace IDs per window; missing/clipped links remain missing. Unsupported branches abstain and contribute no evidence; no positive evidence produces no lead. | Reconstructed E4 combined-evidence family, informed by MoCE weighted expert combination; the five backend branches are not MoCE's client experts. |

These are six generic reconstructed templates, not the paper's unavailable eleven original seeds. MoCE contributes methods only where backend fields support them; no client cohorts, sessions, user actions, URLs, or device attributes are synthesized. KPI selection is telemetry-backed and frozen without labels; the source does not specify the original KPI rule.

The generated-operator worker (`e4core.sandbox`) runs code in a separate bubblewrap process with a narrow JSON API, bounded CPU/time/memory/output, read-only runtime values, and only mounted public inputs/temp output. Syntax and result contracts are checked; AST checks supplement OS isolation. Model-generated code must not receive evaluator data, host credentials, other cases, or network access. M4 library admission is not part of M3.

## Local model and commands

The pinned offline launcher is `scripts/run_m3_model.py`. It verifies the profile's model manifest/hash, pinned llama.cpp revision, libraries, GPU reserve, and local-only server URL; server and client share a network-isolated namespace. Gemma and Devstral profiles both declare 32,768 context tokens, 8,192 max generation tokens, seed 42, serial requests, and a 3,072 MiB free-VRAM reserve. Their decoding/reasoning settings are model-specific in `config/gemma_m3_inference.json` and `config/devstral_inference.json`; common limits do not imply identical decoding. A run creates a unique artifact directory under `artifacts/m3/model_runs/`.

Frozen synthetic comparison commands:

```sh
.venv/bin/python scripts/run_m3_model.py --profile config/gemma_m3_inference.json -- \
  .venv/bin/python scripts/run_m3_benchmark.py --suite config/m3_synthetic_suite_v3.json
.venv/bin/python scripts/run_m3_model.py --profile config/devstral_inference.json -- \
  .venv/bin/python scripts/run_m3_benchmark.py --suite config/m3_synthetic_suite_v3.json
```

The development runner is `scripts/run_m3_development.py`; it accepts `--case-id`, `--split dev`, `--profile`, `--run-id`, and optional `--root`. Its Python implementation is `e4core.development.run_development_dag(case_id, split, profile_path=..., run_dir=..., root=...)`. The model launcher owns the unique model-run directory under `artifacts/m3/model_runs/<run-id>` and binds it as `E4_RUN_DIR`; the development runner writes under its `development/` child. Each development run records `dev_manifest.json` before its first model call, appends full calls to `model_calls.jsonl`, saves the accepted DAG as `model_dag.json`, writes the replay/result record to `development_run.json`, and tracks phase status in `phase_status.json`. A direct CLI invocation, when a model endpoint is running, has this form:

```sh
.venv/bin/python scripts/run_m3_model.py --profile config/gemma_m3_inference.json -- \
  .venv/bin/python scripts/run_m3_development.py --case-id <frozen-dev-id> --split dev \
  --profile config/gemma_m3_inference.json --run-id <unique-run-id>
```

The analogous development launcher profile is `config/devstral_inference.json`. Use a unique run ID and the launcher for real inference so the model and child share the isolated namespace. Full-library prompt calibration is separate: append `--calibrate` to the child `scripts/run_m3_benchmark.py` command; it is not one of the 20 tasks. The corrected synthetic comparison selected Gemma for the first development integration; its fresh-process cache parity replay passed. The separate trusted development-only assessment is recorded in [M3_RESULTS.md](M3_RESULTS.md). M3 is complete; this single case does not establish a Telecom accuracy trend.

Replay a saved DAG on its frozen public development case without another model request:

```sh
.venv/bin/python scripts/run_m3_development.py --case-id <frozen-dev-id> --split dev \
  --replay-dag artifacts/m3/model_runs/<model-run-id>/development/model_dag.json \
  --run-id <unique-replay-id> --root . --verify-cache-parity
```

The replay record is written under `artifacts/m3/dev/<unique-replay-id>/replay/`. It reloads and hash-verifies the public telemetry once, then compares cold, warm, and cache-disabled execution against the same in-memory object. The final saved-DAG replay ran in a fresh process under the source and hash-seed settings recorded in [M3_RESULTS.md](M3_RESULTS.md), with no model call; all three serialized answers matched exactly.

The frozen synthetic comparison uses 20 distinct tasks: eight DAG compositions, six generated operators, four synthetic diagnoses, and two schema/formatting tasks. Repairs are limited to two per diagnostic attempt and may use only static syntax/schema/verifier errors, not semantic checker feedback. Gemma 31B Q4_0 and Devstral 24B Q5_K_M were run serially on the V100 with the shared limits above; the corrected offline replay selected Gemma for development integration. See [M3_RESULTS.md](M3_RESULTS.md) for raw and corrected comparison scores and retained cost records. The eventual Telecom primary metric is component top-three under any of three attempts; five leads are retained internally. Category match is secondary and unknown/null when no classifier is implemented. This M3 runbook does not authorize scored runs or M4's attempt controller.

## Known gaps to carry forward

Original E4 operator source and eleven original seeds are unavailable. The source does not specify the alert KPI, and the reference period may contain abnormal behavior. Absolute `elapsedTime`/`avg_time` units and the precise physical meaning of source duration columns remain unresolved; cross-field arithmetic is excluded. HF mirror provenance is recorded in preparation artifacts, but absolute elapsed-time unit declarations remain unresolved. The six seeds and analysis operators are a validated reconstruction where supported, not a claim of paper-code fidelity. The first development-run and trusted single-case assessment are recorded in [M3_RESULTS.md](M3_RESULTS.md); they do not replace scored-set evaluation.
